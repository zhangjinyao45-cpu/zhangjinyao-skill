## 一、通用规律

### 1. 节点共性

- 大多数节点都支持引用上游节点的输出变量，常见引用方式为固定值或变量引用。
- 很多节点都有固定的输入/输出结构，尤其是插件节点、工作流节点、知识库写入/检索节点，不支持完全自定义输出。
- 复杂类型的参数通常支持 `Object`、`Array`，但不同节点的深度和类型支持不同。
- 工作流中经常会出现“中间消息输出”和“最终结果输出”两种概念：
  - `输出节点`：执行过程中发消息。
  - `结束节点`：返回工作流最终结果。

### 2. 异常处理共性

多数执行类节点都支持异常处理配置，核心模式基本一致：

- `中断流程`：节点失败即停止整个工作流。
- `返回设定内容`：失败后不打断流程，返回预设 JSON，同时附带 `isSuccess`、`errorBody`。
- `执行异常流程`：失败后跳转到异常分支，异常信息通过 `isSuccess`、`errorBody` 传递。

常见补充项：

- 可设置 `超时时间`
- 可设置 `重试次数`，通常最多 1 次
- 某些节点支持 `忽略异常`，即失败也继续走下游，但下游会拿到默认输出

### 3. 平台级限制

- 单个工作流最多添加 `1000` 个节点。
- 单次运行中，所有节点总执行次数最多 `1000` 次，循环次数也计算在内。
- 应用里最多可添加 `100` 个工作流和 `100` 个对话流。
- 若未开启异步运行，建议把单次工作流执行控制在 `5 分钟` 内。
- 智能体连续两次回复的时间间隔限制为 `10 分钟`，超过后端可能判定工作流超时。
- 节点可配置的超时时间上限不同，端插件类插件节点无超时时间限制。

### 4. 类型与变量的高频坑

- Array 类型参数建议引用上游节点输出；直接填固定值时通常会被当成 `String`。
- 多分支场景下，未执行分支的变量会是空值，下游应优先使用 `变量聚合节点` 做统一收口。
- SQL/数据库相关节点在调试阶段使用测试数据，不会直接改动真实数据库。
- 工作流嵌套工作流时，子工作流版本不会自动同步到父工作流。

## 二、节点分类速览

### 1. 基础节点

- 开始节点：定义工作流入口参数。
- 结束节点：定义工作流最终输出。
- 输入节点：运行中向用户补采信息。
- 输出节点：运行过程中向用户发送中间消息。

### 2. 逻辑与编排节点

- 选择器节点：条件分支。
- 意图识别节点：基于模型做意图分类并分流。
- 循环节点：串行重复执行。
- 批处理节点：并行批量执行。
- 变量聚合节点：将多分支结果汇总为统一变量。
- 工作流节点：调用子工作流。

### 3. 智能能力节点

- 大模型节点
- 插件节点
- 代码节点
- 问答节点
- 文本处理节点
- JSON 序列化节点

### 4. 数据与知识节点

- SQL 自定义节点
- 新增数据节点
- 查询数据节点
- 更新数据节点
- 删除数据节点
- 变量赋值节点
- 知识库写入节点
- 知识库检索节点
- HTTP 请求节点

## 三、节点逐项总结

## 3.1 开始节点

### 作用

- 工作流起始节点。
- 定义启动工作流所需的输入参数。
- 默认包含 `BOT_USER_INPUT`，表示用户本轮原始输入。

### 怎么用

- 添加输入参数，配置名称、类型、描述、是否必选。
- 支持直接加字段，也支持导入 JSON 批量生成参数。
- 适合把用户 Query、业务上下文、外部传入结构化数据统一建模为工作流入参。

### 注意事项

- `Object` 最多支持 `3` 层嵌套。
- 必选参数缺失时，工作流无法启动。
- 若工作流绑定到智能体中，模型会根据参数描述自动尝试从 Query 中抽取值，所以描述要写清楚。

## 3.2 结束节点

### 作用

- 工作流最终收口节点，决定最终返回给外部的结果。

### 怎么用

- 支持两种返回方式：
  - `返回变量`：输出 JSON，适合卡片、子工作流、结构化消费场景。
  - `返回文本`：直接输出自然语言，适合对话型场景。
- 返回文本时可引用输出变量，格式为 `{{变量名}}`。

### 注意事项

- 返回变量更适合做“子工作流接口”。
- 如果工作流直接绑定智能体，返回变量模式下模型会自动总结 JSON 再回复用户。
- `Object` 类型参数同样最多支持 `3` 层嵌套。

## 3.3 输入节点

### 作用

- 在工作流运行过程中主动向用户补采缺失信息。
- 执行到该节点时流程会暂停，直到收集到所需参数。

### 怎么用

- 定义输入变量名、类型、描述、是否必选。
- 常用于上游拿不到城市、日期、联系方式等关键信息时补采。

### 注意事项

- 收集到全部必选参数后，工作流才会继续。
- 适合“流程中断后等待用户继续”的交互型工作流。
- 如果只是启动前就能拿到的信息，优先放在开始节点，不要滥用输入节点。

## 3.4 输出节点

### 作用

- 在工作流执行过程中向用户发送中间消息，例如“正在处理中”“请稍候”等。

### 怎么用

- 配置输出变量。
- 配置输出内容，支持通过 `{{变量名}}` 引用变量。
- 可开启流式输出，形成打字机效果。

### 注意事项

- 输出节点是“中间反馈”，不是最终结果返回。
- 流式输出只有在大模型节点之后才能开启。
- 若绑定卡片，即使开启流式，卡片本身仍是非流式展示。
- 一个工作流里有多个流式输出节点时，按执行顺序依次输出。

## 3.5 大模型节点

### 作用

- 用大语言模型处理文本理解、生成、总结、改写、结构化抽取等任务。

### 怎么用

- 选择模型，并按需配置模型参数。
- 配置输入变量，必要时开启对话历史。
- 编写系统提示词和用户提示词。
- 选择输出格式：
  - 文本
  - Markdown
  - JSON
- 若模型支持视觉理解，可单独配置图片类输入。
- 可给模型挂载技能：
  - 插件
  - 工作流
  - 知识库

### 注意事项

- 技能模式下，模型会自动决定何时调用插件/工作流/知识库，灵活但不如显式编排稳定。
- 不支持 Function Call 的模型，不能挂技能。
- 大模型节点的技能暂不支持端插件、也不支持包含中断节点的工作流。
- 需要图片理解时，应使用“视觉理解输入”，不要把图片塞进普通输入参数。
- 开启流式输出后，一旦开始出流，出现异常时不能再重试，也不能跳异常分支。
- 默认超时 `180s`，可调范围 `0.1s~600s`。

## 3.6 插件节点

### 作用

- 调用插件中的具体工具，完成外部能力接入。

### 怎么用

- 在画布中选择插件节点并指定要调用的插件。
- 根据插件工具定义，为必选参数指定固定值或上游变量。
- 输出结构由插件工具定义决定。

### 注意事项

- 输入/输出结构取决于插件本身，不支持任意自定义。
- 适合明确知道何时调用、如何传参的场景。
- 需要批量执行插件时，应搭配批处理节点。
- 批量并行调用时，不要超过插件自身频率限制。
- 默认超时 `600s`，是常见节点里较大的一个。

## 3.7 工作流节点

### 作用

- 在一个工作流中调用另一个工作流，实现子工作流复用。

### 怎么用

- 选择已发布的子工作流。
- 根据子工作流定义好的输入结构传参。
- 输出结构跟随子工作流定义。
- 支持开启批处理模式，批量多次运行该子工作流。

### 注意事项

- 子工作流发布新版本后，父工作流不会自动升级。
- 更新子工作流后，应重新调试父工作流，再手动更新引用版本。
- 如果同一个父工作流里多处引用同一子工作流但版本不一致，可能触发版本冲突报错。
- 支持忽略异常，失败时继续走下游并使用默认输出。

## 3.8 代码节点

### 作用

- 用 Python 编写自定义逻辑，完成复杂加工、类型转换、外部请求或中间计算。

### 怎么用

- 在输入区域声明代码需要的参数。
- 在代码里通过 `args.params['变量名']` 取值。
- 通过 `return` 返回对象。
- 输出结构要与代码返回对象保持一致。
- 可使用 IDE 调试，并把“原始输出”同步回节点定义。

### 注意事项

- 仅支持 `Python`。
- 必须返回对象，即使只有一个值也不例外。
- 不支持多个函数风格的随意组织，应遵循平台规定入口。
- 单请求上限 `1800s`。
- 每个工作流最多 `50` 个代码节点。
- 暂不支持 `HTTP/HTTPS` 以外协议。
- 推荐使用 `asyncio.sleep()`，不要用 `time.sleep()` 阻塞工作流。
- 不要通过遍历所有变量来找入参，容易把系统变量如 `tako_bot_userhistory` 也读进来。

## 3.9 选择器节点

### 作用

- 典型 `if-else` 条件分支节点。

### 怎么用

- 配置“如果 / 否则”条件。
- 每个分支支持多个判断条件，条件间可以是且/或。
- 支持多个分支，并可通过拖拽调整优先级。

### 注意事项

- 适合基于确定规则做路由。
- 如果判断逻辑依赖模型语义理解，优先考虑意图识别节点。
- 分支优先级会影响命中结果，重叠条件需显式排序。

## 3.10 意图识别节点

### 作用

- 使用模型把用户输入归类到不同意图，再分流到不同分支。

### 怎么用

- 选择模型。
- 指定待识别输入，通常引用开始节点中的用户 Query。
- 配置多个意图分类，最多 `50` 个。
- 可追加系统提示词，增强分类准确率。
- 输出固定为：
  - `classificationId`
  - `reason`

### 注意事项

- 每个意图分类都必须连接后续处理节点，否则命中后无法继续。
- 建议始终配置兜底策略。
- 多轮对话里可开启历史，但轮数越多 Token 消耗越高。
- 默认超时 `60s`。

## 3.11 循环节点

### 作用

- 串行重复执行一组节点逻辑。

### 怎么用

- 支持三种模式：
  - 使用数组循环
  - 指定循环次数
  - 无限循环
- 使用数组循环时可用内置变量：
  - `item`
  - `index`
- 支持配置中间变量，在每轮迭代后更新并传递到下一轮。
- 循环体内部编排真实执行逻辑。

### 注意事项

- 多轮循环严格串行，不支持并发。
- 不支持循环节点嵌套循环节点。
- 循环体中不能再放批处理节点。
- 无限循环必须通过“终止循环节点”退出。
- 如果只是为了并发批量跑任务，不要用循环，优先批处理。
- 指定循环次数可设置 `1~1000`，超出会被裁剪。

## 3.12 批处理节点

### 作用

- 对数组中的多个元素并行批量执行同一套处理逻辑。

### 怎么用

- 输入必须引用 Array 类型变量。
- 配置：
  - 并行运行数量上限
  - 批处理次数上限
- 在批处理体里放入待重复执行的节点链路。
- 输出通常是数组结构，引用批处理体内部节点的输出。

### 注意事项

- 适合大规模并行处理，同构任务效率高于循环。
- 不支持在批处理节点内再嵌套批处理或循环。
- 同一时刻只能运行一个流式插件或消息节点，所以不要批量并行跑流式节点。
- 并行数量上限最大 `10`。
- 批处理次数上限最大 `200`。

## 3.13 变量聚合节点

### 作用

- 把多条分支上“语义相同”的输出聚合成统一变量。

### 怎么用

- 为每组变量指定聚合策略。
- 当前主要策略是：返回该组中第一个非空值。
- 支持多个分组，每个分组对应一个输出变量。

### 注意事项

- 同一分组内变量类型必须一致。
- 非常适合选择器、意图识别后的收口。
- 目标不是“合并所有值”，而是“从多个候选结果中挑第一个有效结果”。

## 3.14 SQL 自定义节点

### 作用

- 用 SQL92 常用语法直接操作数据库，完成增删改查。

### 怎么用

- 定义 SQL 中需要引用的输入变量。
- 选择数据表。
- 填写一条 SQL，可引用 `{{变量名}}`。
- 输出固定包含：
  - `outputList`
  - `rowNum`
- 异常扩展输出：
  - `isSuccess`
  - `errorBody`

### 注意事项

- 每个节点只支持一条 SQL。
- 调试环境使用测试数据，不是线上真实数据。
- `GROUP_CONCAT` 结果会受 `group_concat_max_len=1024` 限制。
- 拼接、复杂计算等逻辑不建议在 SQL 节点里做，宜查询后交给代码节点处理。

## 3.15 新增数据节点

### 作用

- 图形化执行数据库 `INSERT`。

### 怎么用

- 选择数据表。
- 选择字段并设置字段值，可用固定值或上游变量。
- 每次执行插入一行。

### 注意事项

- 只支持操作一张表。
- 比 SQL 自定义节点更适合低代码场景。
- 调试环境依然是测试数据。
- 输出重点关注 `outputList` 和 `rowNum`。
- **去重场景**（如白名单数据库）：自定义字段无法设唯一键，平台不会自动去重。若业务需要某字段唯一，**必须在新增前用查询数据节点(43)检查是否已存在**，然后用选择器(8)判断 `outputList` 不为空(operator=10)来分支——已存在则跳过插入，不存在则执行新增。

## 3.16 查询数据节点

### 作用

- 图形化执行数据库 `SELECT`。

### 怎么用

- 选择数据表。
- 配置查询字段、查询条件、排序方式、查询上限。
- 支持等于、不等于、LIKE、IN、IS NULL 等操作符。

### 注意事项

- 模糊查询会自动补 `%值%`，不用手写通配符。
- 默认查询上限 `100`，最大 `1000`。
- 查询输出里 `rowNum` 固定为 `null`。**不能用 `rowNum` 判断是否查到数据**，应用选择器(8)直接判断 `outputList` 不为空(operator=10)或为空(operator=9)。SQL 自定义节点(12)的 `rowNum` 同样为 null。而更新(42)/新增(46)/删除(44)节点的 `rowNum` 正常返回影响行数，可用于分支判断。
- 仍然使用测试数据调试。

## 3.17 更新数据节点

### 作用

- 图形化执行数据库 `UPDATE`。

### 怎么用

- 选择数据表。
- 配置更新条件。
- 选择要更新的字段并设置新值。

### 注意事项

- 至少要有一个更新条件。
- 会更新所有符合条件的数据，不是只更新第一条。
- 模糊查询自动补通配符。
- 调试环境不改真实表。

## 3.18 删除数据节点

### 作用

- 图形化执行数据库 `DELETE`。

### 怎么用

- 选择数据表。
- 配置删除条件。

### 注意事项

- 至少要有一个删除条件。
- 会删除所有符合条件的数据。
- 调试环境不改真实表。
- 与更新节点类似，输出里 `rowNum` 返回实际删除的行数，可直接用于选择器分支判断。

## 3.19 变量赋值节点

### 作用

- 给用户变量或应用变量写值，实现状态持久化、流程控制或记忆更新。

### 怎么用

- 在输入中选择要赋值的目标变量。
- 设置变量值，可为固定值或上游输出。
- 常见用途：
  - 记录用户状态
  - 保存中间结果
  - 控制后续流程分支

### 注意事项

- 只能给用户变量、应用变量赋值，不能改系统变量。
- 除开始节点、输入节点、知识库写入节点外，其他节点通常都能读取变量值。
- 适合实现“跨节点、跨轮次”的轻量状态管理。

## 3.20 知识库写入节点

### 作用

- 在工作流执行期间，把文件或文档写入知识库。

### 怎么用

- 输入固定为 `knowledge`，类型为 `File/Doc`。
- 选择目标知识库。
- 配置解析策略和分段策略。
- 输出固定为：
  - `documentId`
  - `fileName`
  - `fileUrl`

### 注意事项

- 每次执行只能上传一个文件。
- 如果要批量写入，需要配合循环或批处理。
- 这是用户在工作流里上传知识到知识库的唯一途径。
- 该节点是异步节点，上传发起后工作流不必等待它完全处理完成。
- 精准解析更慢，如果下游立刻做检索，可能出现文档尚未解析完导致检索不到。

## 3.21 知识库检索节点

### 作用

- 根据 Query 在指定知识库中检索相关内容，返回召回结果列表。

### 怎么用

- 输入固定为 `Query`。
- 选择一个或多个知识库。
- 配置召回策略：
  - 混合
  - 语义
  - 全文
- 可配置：
  - 最大召回数量
  - 最小匹配度
  - 查询改写
  - 结果重排
  - 仅查看个人文档
- 表格知识库场景下可开启 SQL 查询。
- 输出固定为 `outputList` 数组，元素里含：
  - `output`
  - `documentId`

### 注意事项

- 对话流里可开启会话历史，提升多轮语义检索准确性。
- 查询改写默认开启，但这会额外增加一轮模型处理。
- 结果重排适合对精度要求高的场景，但会增加处理成本。
- 表格 SQL 查询暂不支持跨表 `JOIN`。
- 与“大模型节点挂知识库”不同，知识库检索节点是显式、必然执行的。

## 3.22 HTTP 请求节点

### 作用

- 对外发起 HTTP 请求，获取、提交、更新或删除外部数据。

### 怎么用

- 配置 API 地址和方法。
- 配置请求参数、请求头、鉴权、请求体。
- 支持导入 cURL，快速还原请求配置。
- 输出包含响应体、状态码、响应头。

### 注意事项

- 支持 GET、POST、HEAD、PATCH、PUT、DELETE。
- PATCH 的说明文案在原文中存在明显不严谨之处，实际使用应以 HTTP 语义和接口文档为准。
- 若请求体选择 JSON，变量为字符串时要记得加双引号，否则容易报 `Body is not json`。
- 支持异常忽略，失败时可继续走下游并使用预设默认输出。
- 外部 API 有鉴权、超时、频率限制时，要结合重试和超时配置设计。

## 3.23 问答节点

### 作用

- 通过对话形式主动收集用户信息或引导用户选择意图。

### 怎么用

- 两种模式：
  - `直接回答`
  - `选项回答`
- 直接回答模式：
  - 提问开放式问题
  - 默认输出 `USER_RESPONSE`
  - 可开启字段提取，把用户自然语言回复抽成结构化变量
- 选项回答模式：
  - 配固定选项或动态选项
  - 默认输出 `optionId`、`optionContent`

### 注意事项

- 直接回答模式下，如提取不到必填字段，系统会继续追问。
- 最多回答次数默认 `3`，可设置 `1~5`。
- 选项回答模式下，所有选项都要有后续分支或兜底处理。
- 如果用户回复与选项不匹配，应准备兜底策略。
- 这是典型的“中断型节点”，不适合挂在需要完全自动执行的子工作流里。

## 3.24 文本处理节点

### 作用

- 对字符串做轻量拼接或拆分。

### 怎么用

- 两种处理方式：
  - 字符串拼接
  - 字符串分隔
- 拼接时支持引用：
  - `{{变量名}}`
  - `{{变量名.子变量名}}`
  - `{{变量名[数组索引]}}`

### 注意事项

- 适合轻量字符串编排，不适合复杂结构转换。
- 直接引用数组时会默认用逗号连接。
- 如果需求是结构化拼装或复杂数组操作，优先代码节点。

## 3.25 JSON 序列化节点

### 作用

- 把 `Object`、`Array` 等复杂结构转成 JSON 字符串，供下游节点使用。

### 怎么用

- 输入待序列化变量。
- 输出固定为 `output`，类型为 `String`。

### 注意事项

- 适合把复杂对象写入数据库 String 字段。
- 本质是类型转换节点，不负责结构清洗或格式修复。
- 如果下游本来支持对象或数组，就不要多做一次序列化。

## 四、选型建议

### 1. 大模型节点 vs 插件节点 vs 工作流节点

- 大模型节点挂技能：更灵活，模型自己决定怎么调工具，但稳定性依赖模型判断。
- 插件节点：执行路径最明确，最适合强确定性流程。
- 工作流节点：适合把复杂子流程封装成可复用模块。

### 2. 循环节点 vs 批处理节点

- 循环节点：串行、有状态、适合依赖上一次结果的迭代。
- 批处理节点：并行、无状态、适合数组批量任务。

### 3. SQL 自定义节点 vs 图形化数据库节点

- SQL 自定义节点：自由度高，适合复杂查询或动态 SQL。
- 新增/查询/更新/删除数据节点：门槛低，适合标准 CRUD。

### 4. 输入节点 vs 问答节点

- 输入节点：偏“表单式”收参。
- 问答节点：偏“自然对话式”收集意图或字段。

### 5. 输出节点 vs 结束节点

- 输出节点：过程反馈。
- 结束节点：最终返回。

## 五、高频坑位清单

- 子工作流更新后，父工作流不会自动升级版本。
- 同一父工作流中多处引用同一子工作流但版本不一致，会报版本冲突。
- Array 参数直接填固定值容易变成 String，建议先用代码节点转类型。
- 多分支输出不要直接接结束节点，优先用变量聚合节点统一收口。
- 知识库写入是异步的，写完立刻检索可能检不到。
- 输出节点的流式能力不是所有场景都生效，卡片仍会一次性展示。
- 大模型节点开启流式输出后，异常处理能力会变弱。
- 代码节点尽量不要使用阻塞式 `sleep`。
- 批处理并行数不能只看工作流性能，还要看目标插件/API 的限流。
- 数据库相关节点在调试期是测试数据，不要把调试结果当成线上真实行为。
